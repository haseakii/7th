# v2.2 Plan - ALAS-Style Foundation Refactor

## Goal

v2.2 focuses on making the current `7th` automation codebase easier to extend in the ALAS style. The release should preserve the current `SecretShop` behavior while introducing clearer task registration, stable scheduler contracts, shared frame processing, and reusable vision profiles.

This is an infrastructure release. It should not add a new gameplay module yet.

## Current State

- The active code lives under `7th/`.
- `main.py` chooses between WebUI and ALAS mode, but `--config` is not fully wired into the ALAS path.
- `alas.py` runs `E7AutoScript`, loads `E7Config`, connects `DeviceController`, discovers tasks through `config.get_next()`, and dispatches by method name.
- `SecretShop` currently enters through `E7AutoScript.secret_shop()`, which instantiates `tasks.secret_shop.SecretShopTask`.
- `shop_bot.py` still owns a lot of feature orchestration: navigation, resource checks, OCR usage, scrolling, purchasing, and recovery.
- `DeviceController` already has screenshot/control strategies and normalizes screenshots to `1280x720`.
- OCR is a module-level singleton under `tasks.secret_shop.ocr_engine`.
- Scene, popup, and ROI constants are spread across `shop_bot.py`, `navigator.py`, `purchase.py`, `recognizer.py`, and `scene_manager.py`.

## Design Principles

- Keep ALAS compatibility ideas, but avoid copying ALAS internals blindly.
- Keep existing `SecretShop` behavior stable during the refactor.
- Prefer explicit task metadata over dynamic method discovery.
- Keep `E7Config` as the single persisted configuration surface.
- Make reusable infrastructure live under `module/`; keep gameplay-specific logic under `tasks/`.
- Do not make WebUI depend on private implementation details of task classes.

## Phase 1 - Task Registry and Scheduler Contract

### Target

Replace direct method-name dispatch with a small task registry while keeping existing config files compatible.

### Implementation

- Add a task registry module, suggested path: `7th/module/task/registry.py`.
- Define a task metadata structure with:
  - `command`: scheduler command name, for example `SecretShop`
  - `method`: snake_case runtime name, for example `secret_shop`
  - `factory`: callable that builds the task runner
  - `description`: short display text for logs/WebUI
  - `enabled_by_default`: bool used by config generation later
- Register `SecretShop` as the first task.
- Keep `Scheduler.Command` as the source of truth in existing JSON config.
- Convert `Scheduler.Command` to registry lookup first.
- Keep fallback to the existing `E7AutoScript.<snake_case>()` method for one release to avoid breaking old behavior.
- Log a warning when fallback dispatch is used so future cleanup is visible.

### Acceptance Criteria

- Existing `SecretShop` config runs without JSON migration.
- `E7AutoScript.run("secret_shop")` still works.
- A new registered task can be dispatched without adding a method to `E7AutoScript`.
- Unknown commands fail with a clear `ScriptError` or logged critical error, not an `AttributeError`.

## Phase 2 - Entry Point and Runtime Ownership

### Target

Make `E7AutoScript` the only top-level runtime in ALAS mode. `ShopBot` remains feature implementation, not a parallel scheduler/runtime.

### Implementation

- Update `main.py` so `--config` or a new `--config-name` path is consistently passed into `_run_alas()`.
- Keep default config name as `default`.
- Treat `--alas` as a compatibility flag; no behavior difference from no args.
- Confirm WebUI `ProcessManager` starts `E7AutoScript(config_name=...)` for scheduler mode.
- Keep `ShopBot.start()` for compatibility if WebUI or tests still call it, but do not use it from `E7AutoScript`.
- Make `SecretShopTask` or the existing task wrapper call the feature logic synchronously from the scheduler.

### Acceptance Criteria

- `python main.py` starts the scheduler with default config.
- `python main.py --webui` still starts WebUI.
- The selected config name is consistent between CLI and WebUI subprocess execution.
- There is one scheduler loop in ALAS mode.

## Phase 3 - FrameContext and OCR Reuse

### Target

Reduce duplicate screenshots and repeated OCR calls inside one task loop.

### Implementation

- Add a frame context module, suggested path: `7th/module/vision/frame.py`.
- Define `FrameContext` with:
  - `image`: normalized BGR screenshot
  - `created_at`: timestamp
  - `scene`: optional cached scene result
  - `ocr_cache`: mapping keyed by `(region, min_confidence, mode)`
- Add `DeviceController.capture_frame()` that returns a new `FrameContext`.
- Keep `DeviceController.screenshot()` unchanged for compatibility.
- Add OCR helper methods that accept either raw image or `FrameContext`.
- Cache OCR results only inside one `FrameContext`; never persist OCR cache across screenshots.
- Update `SceneManager.detect()` to accept either `np.ndarray` or `FrameContext`.
- Start by using `FrameContext` in high-value paths only:
  - scene detection
  - popup detection
  - resource checks
  - purchase confirmation checks

### Acceptance Criteria

- Existing tests using raw `np.ndarray` still pass.
- Code can share one screenshot across scene detection and OCR checks.
- A new screenshot creates a new cache.
- OCR backend initialization remains lazy and singleton-compatible.

## Phase 4 - Vision Profiles and ROI Cleanup

### Target

Move hard-coded coordinates and thresholds into shared profile objects so future tasks do not duplicate constants.

### Implementation

- Add a profile module, suggested path: `7th/module/vision/profile.py`.
- Define a base `ScreenProfile` for `1280x720`.
- Define `SecretShopProfile` with:
  - scene detection ROIs
  - popup ROIs
  - resource ROIs
  - refresh button region
  - scroll regions
  - brightness thresholds
  - default confirm/cancel positions
- Replace duplicated constants gradually:
  - `scene_manager.py` first
  - `navigator.py` second
  - `shop_bot.py` third
  - `purchase.py` and `recognizer.py` only where the meaning is clearly shared
- Keep module-level aliases temporarily if tests import constants directly.

### Acceptance Criteria

- Existing imports of important constants do not break during v2.2.
- Scene detection and navigation use the same threshold values.
- Future profile changes can be made in one place for shared regions.

## Phase 5 - Config and WebUI Stability

### Target

Keep config reload and WebUI process behavior stable while the scheduler internals change.

### Implementation

- Keep `E7Config.get_next()`, `task_delay()`, `task_call()`, and `task_stop()` public behavior unchanged.
- Add task registry integration inside scheduler dispatch, not inside config parsing.
- Do not change existing `config/default.json` structure in v2.2 unless required.
- Keep `Scheduler.Command` values as display/runtime command names.
- Preserve `ProcessManager.run_process()` behavior:
  - `func == "alas"` runs the scheduler loop
  - `func == "SecretShop"` may continue to run scheduler mode for compatibility
  - direct function calls should route through the registry when possible
- Add clear logs for selected task, command, registry hit/miss, and next run update.

### Acceptance Criteria

- WebUI can start and stop the scheduler subprocess.
- Editing config still affects future scheduler iterations.
- `Scheduler.NextRun` serialization remains string-based.
- `RequestHumanTakeover`, `TaskEnd`, `GameStuckError`, and `ScriptError` behavior remains compatible with v2.1.

## Test Plan

  - resolving by `Command`

  - OCR cache key includes region and confidence
  - raw image compatibility remains
- Add tests for profile constants:

  - old constant aliases still match profile values

### Integration Checks

- Run scheduler initialization with mocked device connection.

## Migration Notes

- No user config migration is required for v2.2.
- Existing `Scheduler.Command = "SecretShop"` remains valid.
- Existing `SecretShop` settings remain under `SecretShop.*`.
- Any deprecated direct method dispatch should remain available for v2.2 and be removed no earlier than v2.3.

## Risks

- Task registry can accidentally diverge from config command names.
- Frame caching can return stale OCR if reused after a new screenshot.
- Moving constants can break tests or external imports.
- WebUI subprocess behavior may differ from CLI because it runs through `ProcessManager`.

## Rollout Order

1. Add task registry with `SecretShop` registration and fallback dispatch.
2. Add scheduler tests around registry dispatch.
3. Wire CLI config name behavior.
4. Add `FrameContext` without changing existing call sites.
5. Migrate `SceneManager` to accept `FrameContext`.
6. Add `SecretShopProfile` and migrate shared scene/navigation constants.
7. Migrate selected OCR-heavy paths to use frame caching.
8. Run full tests and fix regressions.
